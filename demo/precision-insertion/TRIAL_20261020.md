## Controller cause and code change

The stock AutoDex FR3 follower and this checkout both slept 20 ms **after**
state/FK/command work, producing a slower wall-clock tick than intended. Both
also advanced the path reference only when the next point was within
`max_lead` of the measured arm. If the measured arm was already ahead of a
frozen reference, the same distance test prevented the reference from
catching up. Feedforward could keep commanding motion while the reference
remained frozen. The demo's measured-endpoint check exposed the unfinished
stream instead of treating it as an arrived transfer. Removing that check
would not repair the motion.

The follower now uses measured tick time, sleeps only the remaining part of
the 20 ms period, lets the reference catch up at normal path rate when the arm
is near a later waypoint, and suppresses feedforward when the reference is
clamped. It keeps the existing joint speed, command acceleration, and measured
arrival rules. A read-only simulation using the archived 132-point transfer
path reproduced the old reference stall and let the revised reference reach
the endpoint. This is **not** a physical validation of motion smoothness.

The operator also observed the approaching hand hit the key. No approach
controller trace was saved, so the record cannot isolate approach speed from
pose, adapter geometry, or the planned grasp path as its cause. The existing
near-object/held speed cap is 0.5; it is an absolute cap for held motion,
not a second multiplier. Proximity uses hand-link origins versus the key mesh
surface, with a wrist fallback when the mesh query is unavailable; it is not
a measured fingertip-surface gap. This trial does not establish a safe faster
approach setting.

## 384×288 lift VLM change

The concise post-lift prompt asks the model to inspect the after image first,
locate the small white key relative to the board and hand, and label a key
still on the board as `miss`. The white cup is identified as the socket.
Using the saved **real** before/after image pairs from the false positive
trial, one warm read-only distributed replay on the five capture PCs gave:

| Classification input per image | Wall time, five concurrent views | Per-view result |
| --- | ---: | --- |
| 384×288 | 1.221 s | 5/5 `miss` |
| 512×384 | 0.943 s | 5/5 `miss` |
| 640×480 | 1.064 s | 5/5 `miss` |
| 768×576 | 1.259 s | 5/5 `miss` |

The earlier, longer prompt on a local serial replay gave 4/5 false `held`
at 384×288; the host and prompt differ, so these rows are not a matched
latency comparison. The distributed replay shows the shorter prompt fixes
this **one saved negative scene** at 384×288. It does not establish minimum
reliable resolution or true-positive performance. As requested, a visibly
successful grasp will be checked after a later trial. Preinsert, final
inside-socket, and XY verdict accuracy at 384×288 are also unvalidated.

The active board-9 runtime config and generated distributed config now use
